description: 실패한 CI 실행의 원인을 분류하고 코드 결함인 경우에만 최소 수정 PR을 제안한다
---

실패한 CI 실행을 분석한다. 대상 실행 식별자는 프롬프트의 RUN_ID로 전달된다.

## 1단계: 실패 정보 수집

`gh run view <RUN_ID> --log-failed`로 실패한 검사와 오류 메시지를 확인한다. 어떤 잡의 어떤 단계가 어떤 메시지로 실패했는지를 먼저 특정한다. 로그를 추측으로 보완하지 않는다.

## 2단계: 원인 분류

수정에 착수하기 전에 원인을 세 가지 중 하나로 분류한다. 수정할 수 없는 문제를 무리하게 수정하는 것은 무인 실행에서 가장 흔한 낭비다.

| 분류 | 판정 기준 | 처리 |
|---|---|---|
| 코드 결함 | 변경된 소스의 논리·타입·형식 오류로 실패했다 | 3단계로 진행해 수정한다 |
| 불안정 테스트 | 시각, 순서, 외부 응답 등에 의존해 간헐적으로 실패한다 | 수정하지 않는다. 불안정 테스트로 보고한다 |
| 실행 환경 문제 | 러너, 의존성 설치, 캐시, 네트워크의 문제다 | 변경하지 않는다. 원인만 분석해 보고한다 |

불안정 테스트와 실행 환경 문제로 판정한 경우, 판정 근거와 관찰된 증상을 보고하고 종료한다. 브랜치를 만들지 않는다.

## 3단계: 최소 수정

코드 결함으로 판정한 경우에만 수정한다.

- 실패한 검사를 통과시키기 위한 최소한의 변경만 수행한다.
- 다음 두 가지는 금지한다. 첫째, 테스트의 기댓값을 완화하거나 테스트를 건너뛰어 실패를 회피하는 변경. 둘째, 실패와 관련 없는 파일의 변경.
- 소스 코드와 테스트 코드의 수정 기준은 다르다. 소스의 결함은 소스를 고치고, 테스트가 잘못된 사양을 검증하고 있다고 판단되면 고치지 말고 그 판단을 보고한다.

## 4단계: 검증

수정 후 실패했던 검사를 다시 실행해 통과를 확인한다. `npm test` 또는 실패한 검사에 해당하는 명령을 사용한다. 통과하지 않으면 추가 수정을 반복하지 말고 현재까지의 분석을 보고하고 종료한다.

## 5단계: PR 생성

검증을 통과한 경우에만 진행한다.

1. `claude/fix-<원인 요약>` 형식의 브랜치를 생성한다. 기본 브랜치에 직접 푸시하지 않는다.
2. 대상 브랜치에 이미 열린 자동 수정 PR이 있으면 새 PR을 만들지 않고 기존 브랜치에 변경을 추가한다.
3. 명령은 허용 목록에 등재된 형태 그대로 사용한다. 푸시는 `git push origin <브랜치명>` 형식으로 실행한다. 같은 동작이라도 옵션이 추가되면 허용 목록의 접두사와 일치하지 않아 거부된다.
4. PR 본문에는 다음 네 가지를 적는다. 실패한 검사와 오류 메시지, 판정한 원인, 수행한 변경과 그 이유, 검증에 사용한 명령과 결과.
5. PR 생성까지만 수행한다. 병합하지 않는다. 병합은 게이트와 리뷰를 통과한 뒤 사람이 결정한다.

## 행동 범위

- 자동화 브랜치(`claude/fix-`)의 CI 실패는 이 커맨드의 대상이 아니다. 트리거 단계에서 제외되지만, 대상으로 전달된 경우에도 수정하지 않고 보고만 한다.
- 설계 변경이 필요한 실패는 수정 대상이 아니다. 원인을 보고하고 이슈 생성을 제안한다.

## 무인 실행의 전제

이 커맨드는 사람이 없는 자동화 실행에서 호출된다. 승인을 요청할 대상이 없으므로 진행 여부를 묻지 않는다. 허용된 범위에서 수행할 수 있는 일은 끝까지 수행하고, 수행할 수 없는 일은 그 사유를 보고하고 종료한다.
