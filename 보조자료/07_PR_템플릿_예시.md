# PR 템플릿 예시와 작성 지침

에이전트가 만든 변경에서 가장 위험한 것은 코드에 드러나지 않는 **가정**이다. 본문
9장의 minishop 사고에서 개발자 A의 세션은 "할인은 주문의 것", 개발자 B의 세션은
"금액은 품목의 것"이라고 가정했다. 두 구현은 각자 테스트를 통과했으나, 결합한 뒤
장부가 맞지 않았다. 가정은 코드에 기록되지 않은 조건을 진술한 것이므로 코드를
분석해도 드러나지 않는다. 그래서 minishop 팀은 PR 템플릿에 **가정 섹션을 강제로
배치**했다(9.3.3). 이 문서는 그 템플릿(예제 9.11)의 원문과 각 항목이 결합 전 검증에서
맡는 역할을 설명한다.

## 예시 원문 (minishop/.github/pull_request_template.md)

```markdown
# 변경 내용
<!-- 무엇을, 왜 바꿨는지 세 줄 이내로 -->

## 이 PR이 전제하는 것 (가정)
<!-- 코드에 드러나지 않는 가정을 모두 적는다. "없음"도 답이다.
예: 할인은 품목 단위로 배분되어 있다 / 이 API는 재시도해도 안전하다 -->

## 결합 전 확인

- [ ] 관련 계약·명세(specs/)를 확인했고 위반이 없다
- [ ] 다른 팀원이 의존하는 인터페이스를 바꾸지 않았다 (바꿨다면 명세 변경을 포함했다)
- [ ] 계약 테스트를 포함한 전체 테스트가 통과한다
- [ ] 이 변경으로 영향받는 코드의 오너에게 리뷰를 요청했다
```

## 항목별 해설

**변경 내용(세 줄 이내)** — 분량 제한 자체가 점검 역할을 한다. 한 PR의 변경을 세
줄로 설명할 수 없다면 그 PR은 여러 관심사를 담고 있다. 이는 표 10.1의 분할 기준(한
문장 설명 가능성)과 같은 판정이다. "왜"를 적게 한 이유는 에이전트가 작성한 커밋
메시지가 무엇을 바꿨는지는 정확히 기록하지만 왜 바꿨는지는 담지 못하기 때문이다(10.3.1).

**가정 섹션** — 이 템플릿의 존재 이유다. 세 가지 설계가 들어 있다. 첫째, 제목이
"전제하는 것"이므로 작성자가 코드 밖의 조건을 떠올린다. 둘째, **"없음"도 답이다**
라는 문구로 빈칸을 허용하지 않는다. 빈칸으로는 "가정이 없다"와 "생각하지 않았다"를
구분하지 못한다. "없음"이라고 적은 작성자는 최소한 한 번 자문한 것이다. 셋째, 예시
두 개가 가정의 형태를 보여 준다. 할인 배분 단위는 데이터 모델에 관한 가정이고,
재시도 안전성은 외부 동작에 관한 가정이다. 이 섹션은 기계가 대신 작성하지 못한다.
결합 전 검증 체크리스트에서 자동화 열이 "불가능"인 유일한 항목이 가정 명시다. 그래서
템플릿으로 강제한다.

**결합 전 확인 네 항목** — 네 항목의 순서에는 이유가 있다. 첫째 항목인 계약 확인은
명세 부재를 방어한다. 둘째 항목인 인터페이스 변경 여부는 컨텍스트 불일치를 방어한다.
셋째 항목인 계약 테스트 포함 전체 테스트는 자동 검증에 해당한다. 넷째 항목인 오너
리뷰 요청은 CODEOWNERS로 지정된 사람이 계약의 변경을 승인하게 한다. 둘째 항목의 괄호
"(바꿨다면 명세 변경을 포함했다)"는 인터페이스 변경을 금지하는 것이 아니라 **명세와
함께 변경한다**는 규칙이다. 이 규칙은 병합 게이트(예제 9.12)가 pricing.py 변경 시
specs/pricing-contract.md 변경을 요구하는 검사와 짝을 이룬다.

## 게이트와의 관계

템플릿의 확인 항목 가운데 자동화가 가능한 항목은 CI 게이트로 옮겨 사람의 성실성에
의존하지 않게 한다(9.3.3). minishop에서는 계약 테스트 실행과 명세 변경 동반 확인이
게이트로 자동화되어 있고, 템플릿에는 그 결과를 확인했다는 체크만 남는다. 자동화된
항목을 템플릿에서 지우지 않는 이유는 작성자가 결과를 한 번 확인하게 하려는 것이다.

## 자기 팀에 맞출 때

| 항목 | 그대로 두는 것 | 바꾸는 것 |
|---|---|---|
| 변경 내용 | 분량 제한과 "왜" 요구 | 줄 수(세 줄이 표준) |
| 가정 섹션 | 제목, "없음"도 답이라는 문구, 예시 2개 형식 | 예시를 자기 도메인의 가정으로(예: "이 잡은 하루 한 번만 실행된다") |
| 결합 전 확인 | 네 항목의 순서 | 명세 디렉터리 경로, 계약 테스트 이름 |
| 추가 | — | 계획 의무 작업(06)에 해당하면 "계획 요약" 항목을 추가한다 |

항목을 늘릴 때는 신중해야 한다. 체크리스트가 길어지면 형식적으로 전부 체크하는
습관이 생겨 가정 섹션까지 빈칸이 된다. 본문의 계산으로는 체크리스트 10분 × PR 100건이
이틀 남짓이고, 이틀짜리 사고 하나를 방지하면 상쇄된다. 항목을 추가하려면 그 항목이
방지하는 사고가 무엇인지 설명할 수 있어야 한다.

## 운영 신호

- 가정 섹션에 "없음"만 반복되면 작성자가 가정을 점검하지 않은 것이다. 리뷰에서 "정말
  없는가"를 한 번 되묻고, 반복되면 8.4의 공유회에서 가정을 찾는 연습을 다룬다.
- 게이트 위반 수(9.3.3)와 함께 "가정 섹션이 비어 있던 PR에서 발생한 결함"을 집계하면
  이 템플릿의 효과가 측정된다(17.1의 품질·표준 지표).

## 점검

- [ ] 저장소의 `.github/pull_request_template.md`에 배치되어 PR 생성 시 자동으로 채워지는가
- [ ] 가정 섹션의 예시가 자기 팀의 도메인 가정으로 바뀌어 있는가
- [ ] 확인 항목의 경로·테스트 이름이 실제 저장소와 일치하는가
- [ ] 자동화 가능한 항목이 CI 게이트로 옮겨져 있는가
- [ ] 오너 리뷰 요청이 CODEOWNERS와 연결되어 실제로 리뷰어가 자동 지정되는가
