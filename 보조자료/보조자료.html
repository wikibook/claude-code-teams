팀 도입 키트 안내

『팀을 위한 클로드 코드 완벽 가이드』의 문서 양식 팩이다. 클로드 코드를 팀에 도입하고 운영하는 과정에서 필요한 문서 7종(02~08)을, 본문 사례(paylog·notihub· minishop)의 실제 파일을 바탕으로 그대로 채워 쓸 수 있게 묶었다.

이 문서들은 선택 사항이 아니라 본문이 각 단계의 결정을 기록하는 수단으로 제시한 것이다. 파일럿 기준을 문서로 확정하지 않으면 결과에 따라 기준이 바뀌어 파일럿이 끝나지 않는다(6.1.2). 권한 정책을 문서로 두지 않으면 허용 범위가 늘어나기만 한다(14.1). PR 템플릿에 가정 섹션이 없으면 코드에 없는 전제가 결합 시점에야 드러난다(9.3.3). 각 양식은 그 결정을 빠뜨리지 않게 하는 최소 형식이다.

도입 단계별 배치

결정 단계(파일럿 전)에서는 02와 03을 작성한다. 02는 채택·산출·체감의 세 지표와 실패 판정 기준(사용 정착·품질 악화·보안 차단)을 시작 전에 숫자로 확정하는 문서다. 03은 보안 검토가 도입 막바지에 일정을 멈추지 않도록, 학습 사용·보존· 데이터 범위·기술 통제를 근거 문서와 확인일로 미리 정리하는 문서다.

파일럿 단계에서는 05·06·07을 저장소에 배치한다. 파일 이름은 각 문서 머리의 원래 경로(CLAUDE.md, docs/policies/permissions.md, .github/pull_request_template.md)를 따른다. 05는 "무엇을 넣고 무엇을 뺄 것인가"(7.1.1)의 기준대로 반복되는 정보만 담는다. 개인 취향에 해당하는 설정은 개인 설정에 남긴다.

확산 단계에서는 08로 온보딩을 표준화한다. 온보딩 문서는 규칙의 원본이 아니라 읽는 순서와 문의처를 안내하는 문서이므로, 규칙 자체는 05·06에만 둔다.

운영 단계에서는 에이전트 팀을 시험할 때 04를 적용한다. 분기마다 10(자가 진단)으로 표준의 상태를 점검한다. 손익이 세 차례 이상 검증된 작업 유형은 예외에서 표준 사용으로 전환한다.

사용할 때 지킬 것

  • 예시로 적힌 팀·수치·날짜·파일 경로는 본문 사례의 값이다. 조직의 값으로 교체한다.
  • 양식의 항목은 늘리기보다 줄이는 편이 낫다. 본문의 notihub에서는 예외 신청서가 번거로워 구성원이 개인 설정으로 우회했고, 양식을 절반으로 줄인 뒤에야 신청 기록이 실제 사용을 반영하게 되었다(17.3.2).
  • 05·06·07은 저장소에 커밋되는 파일이므로 개정 이력이 Git에 남는다. 표준 수정은 7.5.2의 거버넌스(제안·검토·반영)를 따른다.

파일럿 기준 문서 양식

파일럿의 성패는 도구가 아니라 시작 전에 무엇을 확정했는가에 따라 결정된다. 성공 기준이 없으면 결과에 따라 기준이 바뀐다. 실패 기준이 없으면 성과가 불분명한 상황에서 "조금 더 써 보자"는 결정이 반복되고, 파일럿이 끝나지 않은 채 사실상 정식 도입으로 이어진다(본문 6.1.2). 이 문서는 팀·기간·범위·성공 기준·실패 기준·측정 방법을 파일럿 시작 전에 한 장으로 고정하고, 종료 시점에 같은 문서로 판정하기 위한 양식이다.

작성 전에 정할 것: 파일럿 팀 선정 (6.1.1)

기준 문서를 쓰기 전에 팀이 관찰에 적합한지 먼저 확인한다. 부적합 조건에서 시작하면 도구의 효과와 환경의 문제를 구분할 수 없다.

기준 적합 부적합 이유
규모 개발자 3~8인 1~2인, 15인 이상 너무 적으면 개인 습관과 도구 효과가 섞이고, 너무 많으면 관찰의 질이 떨어진다
코드베이스 테스트가 있고 배포가 자동화된 저장소 검증 수단이 없는 저장소 산출물의 품질을 기존 공정 안에서 확인할 수 있어야 한다
의지 자원자가 있고 리더가 참여 시간을 승인한 팀 지명으로 차출된 팀 자원한 팀이 실패 사례까지 공유한다. 회의적인 구성원 한둘은 오히려 유익하다
일정 통상 업무 기간 대형 릴리스 직전, 비상 대응 중 여유가 없으면 도구를 사용하지 않은 것과 사용할 수 없었던 것을 구분할 수 없다

기간은 4~8주가 적절하다. 첫 주는 설치·인증·기본 사용에 쓰이므로 4주 미만이면 학습 과정만 측정하게 된다. 기간이 너무 길면 임시 실험이 상시 운영으로 굳어진다.

양식

항목별 작성 지침

성공 기준은 세 종류를 모두 둔다(6.1.2). 채택 지표는 다른 지표를 해석하기 위한 전제다. 채택률이 낮으면 산출물이 개선되었더라도 충분한 사용 경험을 확보한 것이 아니다. 산출 지표는 속도와 품질을 함께 본다. PR 수가 늘었는데 반려율과 결함률도 늘었다면 생산성 향상이 아니라 검증 공백의 확대다. 체감 지표는 주간 설문 한두 문항 ("이번 주 에이전트가 시간을 절약하는 데 도움이 되었는가", "다음 프로젝트에서도 계속 사용하겠는가")이면 충분하다. 이 응답은 도구가 실제 업무에 정착할 가능성을 나타낸다.

실패 기준은 성공 기준과 같은 날 정한다. 세 가지 유형이 표준이다. 사용 정착 실패는 4주 차 이후 활성 비율이 절반 아래로 떨어지고 회복되지 않는 경우다. 품질 악화는 속도가 올랐더라도 확산을 멈추는 사유가 된다. 보안 차단은 기술적 성과와 무관하게 종료 사유다. 실패로 판정되면 계약을 정리하고 관찰 기록을 남긴 뒤 종료한다. 실패의 원인과 조건은 다음 파일럿의 설계 자료이므로, 실패도 파일럿의 중요한 결과다.

측정 방법은 시작 전에 확정한다. 착수→병합 시간과 반려율은 저장소와 이슈 트래커에서, 사용량은 조직의 관리 화면에서 수집한다. 파일럿에서는 이 정도의 단순한 수집 체계로 충분하다. 상시 측정 체계로의 확장은 17장의 문제다.

지표를 개인 평가와 분리한다는 문장은 형식이 아니다. 지표가 평가에 쓰인다는 인식이 생기면 채택률과 산출 수치가 왜곡된다. 그 결과 파일럿은 도구를 관찰하는 실험에서 성과를 보여 주는 수단으로 변질된다.

# 파일럿 기준 (작성일: 2026-08-20)

## 대상과 기간
- 팀: 결제 서비스팀(개발자 5명)
- 저장소: paylog
- 기간: 2026-09-01 ~ 2026-10-12 (6주)
- 제외 범위: 운영 데이터베이스 접근, 배포 조작

## 성공 기준 (모두 충족하면 확산 제안)
- 채택: 주간 활성 사용 80% 이상 유지
- 산출: 착수부터 병합까지 걸리는 시간 20% 단축
- 품질: PR 반려율과 결함 발생률이 나빠지지 않을 것
- 체감: "계속 사용하겠다" 응답 70% 이상

## 실패 기준 (하나라도 해당하면 종료)
- 4주 차 이후 주간 활성 사용 50% 미만이 2주 연속
- 결함 발생률이 뚜렷하게 증가하고 원인이 도구로 좁혀짐
- 보안 검토에서 해소할 수 없는 차단 사유 확인

## 측정과 판정
- 측정: 매주 금요일, 운영 책임자가 기록
- 판정: 5~6주 차 데이터를 기준으로 결정
- 지표는 판정에만 사용하고 개인 평가와 분리한다

수치는 조직마다 다르게 정해도 되지만 구조는 같다. 채택을 확인하고, 속도와 품질을 함께 측정하고, 사용자 수용도를 확인한다. 제외 범위에 배포와 운영 DB를 넣은 것은 6.4.2의 실행 범위 통제와 같은 원칙이다. 이 기록은 보안 검토 답변(03)에서 "현재 이 범위에서 이렇게 통제하고 있다"고 서술하는 근거가 된다.

판정 시 점검

  • 성공 기준 네 항목의 실측값이 모두 기록되어 있는가(하나라도 미측정이면 판정을 미루지 말고 "측정 실패"로 기록한다)
  • 산출 지표에서 속도 향상이 품질 악화와 동반되지 않았는가
  • 실패 기준 셋 중 어느 것도 발동하지 않았는가
  • 판정 결과와 근거를 확산 일정(6.1.3)의 첫 판정 지점 기록으로 남겼는가

보안 검토 답변 양식

보안 검토에서 가장 먼저 나오는 질문은 "우리 코드가 모델 학습에 사용되는가"다. 이 질문에 예·아니오로 답하려 하면 논의가 정리되지 않는다. 답은 어떤 계약과 사용 환경으로 서비스를 쓰는지에 따라 달라지기 때문이다(본문 6.4.1). 이 양식은 막연한 질문 ("AI에 코드를 넣어도 되는가")을 검토 가능한 질문("어떤 데이터를 어떤 조건에서 쓸 수 있는가")으로 바꾸는 회신 문서다. 보안팀·법무팀이 그대로 검토할 수 있도록 근거 문서와 확인일을 항목마다 붙인다.

언제, 누가 쓰는가

  • 시점: 파일럿 시작 전. 보안 검토가 도입 막바지에 일정을 멈추는 일(표 B.7 "도입 막바지에 보안 검토로 일정이 중단된다")을 막기 위해 기술 담당이 먼저 작성해 제출한다.
  • 작성: 기술 담당(리드 또는 파일럿 운영자). 검토: 보안팀·법무팀.
  • 파일럿 기준 문서(02)의 제외 범위와 대응한다. 02에서 배포·운영 DB를 제외했다면 이 문서 "승인 요청 범위"의 금지 항목과 일치해야 한다.

양식

항목별 작성 지침

1. 계약과 적용 정책. 소비자용 Free·Pro·Max는 옵트아웃 방식이므로 설정을 끄지 않으면 세션이 모델 개선에 사용될 수 있다. Team·Enterprise·API 같은 상용 서비스는 고객 콘텐츠를 학습에 쓰지 않는 것이 기본이다(6.4.1). 따라서 첫 항목은 "우리는 어떤 계약으로 쓰는가"다. 개인 구독으로 업무에 쓰는 구성원이 있다면 그 자체가 별개의 위험이므로 6.3.1의 사용 현황 목록과 대조한다. 보존은 학습과 별개의 질문이다. 학습에 쓰이지 않아도 즉시 삭제되는 것은 아니므로, 적용 보존 정책과 조정 가능 여부 (Enterprise의 사용자 지정 보존 기간, 적격 계정의 ZDR)를 따로 적는다. 근거 문서와 확인일을 붙이는 이유는 정책이 바뀌기 때문이다. 확인일이 없는 답변은 검토가 끝난 뒤의 유효 기간을 확인할 수 없다.

2. 데이터 범위. 검토 대상은 소스 코드만이 아니다. 대화, 프로젝트 데이터, 연결된 외부 데이터(MCP), 사용량·관리 정보까지 서비스 과정에서 처리되는 정보의 종류를 적는다. 차단 대상에는 이미 훅과 권한 규칙으로 막고 있는 경로(paylog의 .env 보호 훅 같은 실제 설정)를 예시로 제시하면 설득력이 높아진다.

3. 기술 통제. "유출되지 않는다"고 단정하는 대신 에이전트가 어디까지 접근하고 무엇을 실행할 수 있는지를 통제 수단으로 설명한다(6.4.2). 정리 기준은 네 가지 축이다. 접근 범위(permissions.deny와 훅으로 민감 경로 차단), 실행 범위(권한 모드와 샌드박스, 파일럿 범위에서 배포·운영 DB 제외), 통신 범위(네트워크 정책, 필요하면 클라우드 경로로 기존 클라우드의 경계 안에 배치), 정책의 강제(구성원이 임의로 해제할 수 없는 관리 정책 계층)를 각각 적는다. 파일럿 전에 경계를 정해 두었다면 "앞으로 통제하겠다"가 아니라 "현재 이 범위에서 이렇게 통제하고 있다"고 서술한다.

4. 계약 통제. 데이터 처리 부속서(DPA)는 개인정보와 고객 데이터의 처리 관계를 계약상으로 명확히 하는 기본 문서다. 이 항목에서 보존 조건, 감사 지원, 데이터 처리 위치를 확인한다. 규제 요건이 있는 조직은 컴플라이언스 인증과 처리 위치를 확인하고, 필요하면 클라우드 경로(6.2.1)로 기존 클라우드의 보안·네트워크 정책을 그대로 적용한다. 기술 담당은 법무팀과 보안팀이 바로 검토하도록 확인 항목을 먼저 정리하는 역할을 한다.

5. 승인 요청 범위. 이 문서의 결론은 승인 여부가 아니라 사용 경계의 명문화다. 어떤 계정으로, 어떤 저장소에서, 어떤 데이터까지, 어떤 권한과 네트워크 통제 아래 쓸 수 있는지를 허용·조건부 허용·금지로 나눠 적는다. 경계가 문서로 있으면 이후 논의는 "AI 도구를 써도 되는가"에서 "현재 경계를 어떻게 조정할 것인가"로 바뀐다.

팀 실행 예외 신청서

에이전트 팀(멀티에이전트) 실행은 단일 세션보다 토큰 비용이 몇 배로 늘어난다. 사람의 감독 시간이 추가되고 조율 실패의 위험도 커진다. 따라서 팀 실행은 표준 사용이 아니라 사유와 기간을 남기는 예외로 시작한다. 손익이 검증된 작업 유형부터 표준으로 전환한다(본문 15.2.1, 13.3.1). 이 양식은 그 손익 계산을 절차로 고정한 것이다.

판단의 기준: 손익 부등식

팀 실행이 정당화되는 조건은 다음 부등식 하나로 정리된다.

시간 가치 + 품질 이득 > 토큰 비용 + 조율 실패 비용 + 검토 비용 + 감독 비용

좌변을 채울 때 흔히 저지르는 과대평가가 두 가지 있다. 첫째, 시간 가치는 줄인 시간의 길이가 아니다. 장애 조사처럼 지연이 곧 손실인 작업은 한 시간의 값이 크다. 마감에 여유가 있는 백로그 작업은 같은 한 시간을 줄여도 값이 작다. 둘째, 품질 이득은 기존 공정에 추가되는 발견만 계산한다. 게이트(9장)와 단일 리뷰어(11장)가 이미 발견했을 결함은 팀의 이득으로 계산하지 않는다. 우변에서는 감독 시간을 빠뜨리기 쉽다. 팀이 세 시간에 작업을 완료했더라도 사람이 그 세 시간 동안 감독했다면 절약된 시간을 전부 이득으로 볼 수 없다.

- services/api — 알림 API와 발송 파이프라인. 발송 로직의 진실 원천
- services/web — 관리 콘솔 (React)
- packages/shared — 공용 타입과 알림 템플릿 엔진

## 명령
- 명령은 각 작업 공간 디렉터리에서 실행한다 (예: services/api에서 pnpm test)
- 전체 타입 검사는 루트에서 pnpm -r check (커밋 전 훅이 자동 실행)

## 계약
- 발송 규칙(재시도·중복 제거)을 다루는 코드는 specs/delivery-contract.md를 따른다
- 발송 파이프라인의 세부 관례는 services/api/CLAUDE.md를 따른다

## 작업 규약
- 커밋 첫 줄은 "영역: 변경 요약" 형식 (예: api: 재시도 간격 상한 추가)
- 리뷰는 /review, 커밋은 /commit을 사용한다
- 계획 검토가 의무인 작업 유형은 docs/policies/permissions.md를 따른다

## 금지
- 운영 발송 채널 호출 금지 (훅으로 차단됨) — 테스트는 샌드박스 채널 사용
- .env 계열 파일은 읽지 않는다 (권한 규칙으로 차단됨)

전체가 스무 줄 남짓이다. 분량이 짧은 것은 의도된 구성이다. 이 파일은 모든 세션의 시작 컨텍스트에 실리므로(2.6, 4.3), 한 줄이 늘면 팀 전체의 모든 세션이 그만큼을 매번 읽는다.

절별 해설

머리말(무엇을 만드는가) — 두 문장으로 쓴다. 에이전트가 저장소의 목적을 알아야 판단의 방향이 잡힌다. 배경 설명이나 역사는 넣지 않는다.

구조 — 디렉터리 자체가 아니라 디렉터리의 역할을 적는다. "발송 로직의 진실 원천"처럼 어디가 기준인지 밝히는 한 구절이 에이전트의 탐색 순서를 결정한다. 디렉터리 목록 전체를 나열하는 것은 파생 가능한 정보(에이전트가 읽어서 알 수 있는 것)이므로 넣지 않는다(4.1.2, /doctor가 지적하는 항목).

명령 — 실행 위치와 검사 명령을 적는다. "커밋 전 훅이 자동 실행"처럼 사람이 직접 수행하지 않아도 되는 항목을 밝혀 두면 에이전트가 불필요한 명령을 반복하지 않는다. 이 절은 실제 저장소의 스크립트와 문자 단위로 일치해야 한다. 명령 한 줄이 어긋나면 세션마다 실패가 발생한다.

계약 — 팀 파일에서 가장 중요한 절이다. 여러 사람이 동시에 에이전트를 사용하면 세션마다 다른 가정으로 코드가 작성된다. 계약 문서의 위치를 여기에 한 줄로 고정하면 어느 구성원의 세션이든 같은 계약을 참조한다(7.1.1). 지시할 때마다 계약을 언급하는 방식은 기억에 의존하므로 일관성이 깨진다. 하위 디렉터리의 CLAUDE.md로 세부 관례를 위임하는 줄도 여기 둔다. 루트에는 방향을 두고, 세부 관례는 작업 영역에 가까운 파일에 둔다(4.2.1).

작업 규약 — 커밋 형식, 사용할 커맨드, 계획 검토 의무 작업을 적는다. 세부 판정 기준은 정책 문서(06)에 두고 여기서는 위치만 가리킨다. 규약 전체를 여기에 적으면 파일이 길어지고, 정책이 바뀔 때 두 곳을 수정해야 한다.

금지 — 각 항목 뒤에 붙은 "(훅으로 차단됨)", "(권한 규칙으로 차단됨)" 같은 괄호가 핵심이다. CLAUDE.md는 지침을 제공하는 계층이지 실행을 보장하는 계층이 아니다(7.1.1). 컨텍스트가 압축되거나 지침이 누락되어도 반드시 지켜져야 하는 규칙은 훅·권한 규칙으로 강제하고, 여기에는 그 사실을 알린다. 문서에만 있는 금지는 권고에 그친다.

넣지 말아야 할 것 (7.1.1)

  • 수명이 끝난 규칙: 마이그레이션이 끝난 뒤의 "구 API 금지", 담당자가 바뀐 뒤의 "배포 전 OOO에게 확인"은 에이전트를 잘못된 방향으로 이끌고 컨텍스트만 차지한다.
  • 시스템으로 강제해야 하는 규칙: "프로덕션 DB에 접속하지 않는다"는 문서가 아니라 권한 정책이나 훅으로 차단해야 한다. 문서에는 강제된 사실만 알린다.

초안을 만드는 방법

구성원들의 기존 개인 CLAUDE.md에서 공통 항목을 추출한다. 여러 사람에게 반복해서 등장하는 규칙을 후보로 모은 뒤, 두 질문(전원 적용? 세션마다 필요?)으로 거른다. 여러 사람이 독립적으로 같은 지침을 작성했다면 그 규칙은 팀 전체에 해당하는 사실이다. 파일럿을 거친 조직은 파일럿 팀의 파일을 출발점으로 삼되 개인 취향·낡은 규칙·강제 규칙을 제거한다.

점검

  • 각 줄이 두 질문(팀 전원에게 적용되는가, 세션마다 필요한가)을 통과하는가
  • 명령 절의 명령이 실제 저장소에서 그대로 실행되는가
  • 계약 문서의 경로가 실재하며, 계약 문서에 메타 정보·결정·불변식·인터페이스·이유·변경 절차가 있는가(표 9.2)
  • 금지 항목마다 강제 수단(훅·권한 규칙)이 실재하는가(없다면 "금지"가 아니라 "권고"로 옮긴다)
  • 개정 절차가 정해져 있는가(7.5.2). 이 파일의 수정은 CODEOWNERS로 리뷰어를 지정한다

권한 정책 문서 예시와 작성 지침

권한 규칙이 개별 도구 호출의 경계를 정한다면, 권한 모드는 세션 전체의 실행 방식을 정한다. 팀 정책은 이를 한 단계 확장해 어떤 작업에 어떤 모드를 적용할 것인지를 정하는 문서다(본문 7.3.2). 모드 선택의 기준은 작업의 위험도가 아니라 검증 체계의 구조다. 산출물이 테스트와 자동 검증으로 충분히 확인되는 작업은 승인 빈도를 낮춰도 안전하다. 반면 검증이 사람의 판단에 의존하는 작업에서는 승인 자체가 검증 지점이므로, 승인을 줄이는 것이 곧 검증 수준의 저하다. 권한 수준은 리뷰와 테스트가 제공하는 검증 강도에 맞춘다(2.7.2).

# 권한 정책

## 기본 모드
- 이 저장소의 기본 모드는 acceptEdits다 (.claude/settings.json에 설정됨)
- 근거: 전 패키지에 테스트가 있고 커밋 전 검증 훅이 있다

## 계획 검토가 의무인 작업
다음 작업은 플랜 모드로 시작하고, 계획 승인 후 구현한다.
- 저장 형식(스키마·마이그레이션)이 바뀌는 작업
- 공개 API의 추가·변경·삭제
- 발송 파이프라인(services/api/src/dispatch/)의 변경
- 세 개 이상의 작업 공간을 가로지르는 리팩터링
확인: 해당 유형의 PR은 본문에 계획 요약을 포함한다.

## 우회 모드(bypassPermissions)의 사용 조건
- 허용: 자격 증명과 운영 자원에서 격리된 컨테이너·CI 환경
- 금지: 개발자 로컬 기기 (관리 설정으로 차단됨)
- 거부 규칙은 우회 모드에서도 적용된다

## 이 문서의 수정
- .claude/ 경로와 같은 승인 절차를 따른다 (CODEOWNERS 참조)

절별 해설

기본 모드와 근거 — 모드만 적지 않고 근거를 적는 것이 이 문서의 핵심 형식이다. notihub가 acceptEdits를 기본으로 둔 이유는 "전 패키지에 테스트가 있고 커밋 전 검증 훅이 있다"는 검증 체계에 있다. 근거가 사라지면, 즉 테스트가 없는 패키지가 생기면 모드도 다시 판단해야 한다. 근거가 적혀 있어야 분기 점검에서 그 판단을 다시 수행한다. 검증 수단이 부족한 레거시 저장소라면 승인 과정이 주요 검증 수단이므로 default를 기본 모드로 둔다(표 7.7).

계획 검토가 의무인 작업 — 3.1.3의 원리(계획의 가치는 변경을 되돌리는 비용에 비례한다)를 개인의 감각이 아니라 작업 유형으로 구체화한 절이다. 네 유형은 데이터 구조 변경, 공개 인터페이스 변경, 핵심 파이프라인 변경, 범위가 넓은 리팩터링이다. 마지막 줄 "확인: 해당 유형의 PR은 본문에 계획 요약을 포함한다"가 중요하다. 플랜 모드는 세션의 상태이므로 설정만으로 강제되지 않는다. 그래서 PR에서 계획의 존재를 확인하는 방식으로 보완한다. 목적은 특정 모드의 강제가 아니라 되돌림 비용이 큰 작업에 구현 전 검토 지점을 두는 것이다.

우회 모드의 사용 조건 — 금지가 아니라 환경 제한이다. bypassPermissions는 승인 프롬프트를 생략하므로 프롬프트 주입 방어가 약해진다(2.7.1). 따라서 자격 증명과 운영 자원에서 격리된 컨테이너·CI에서만 허용하고, 로컬 기기에서는 관리 설정으로 차단한다. "거부 규칙은 우회 모드에서도 적용된다"는 문장은 권한 모드와 안전 정책이 다른 계층이라는 사실(2.7.2)을 구성원에게 알리는 역할을 한다.

이 문서의 수정 — 정책 문서 자체가 표준이므로 수정에는 .claude/ 설정과 같은 승인 절차를 적용한다(7.5.2). CODEOWNERS로 리뷰어를 지정해 두면 정책이 합의 없이 바뀌는 일을 방지한다.

자기 팀에 맞출 때

  1. 기본 모드는 검증 체계에서 역산한다. 테스트 커버리지와 커밋 전 훅이 있는가를 먼저 확인하고, 그 사실을 근거 줄에 적는다. 근거를 적을 수 없으면 기본 모드는 default다.
  2. 계획 의무 작업은 저장소의 실제 경로로 적는다. "핵심 파이프라인"이라는 일반어 대신 notihub처럼 services/api/src/dispatch/ 같은 경로를 명시해야 해당 여부에 이견이 생기지 않는다.
  3. 우회 모드의 허용 환경을 조직의 실제 CI·컨테이너 이름으로 적는다. 이어서 로컬 차단이 관리 설정(14.3.1)으로 실제로 배포되어 있는지 확인한다. 문서만 있고 설정이 없으면 이 절은 권고에 그친다.
  4. CLAUDE.md의 작업 규약에는 이 문서의 위치만 남긴다(05). 판정 기준의 원본은 여기 한 곳이다.

점검

  • 기본 모드에 근거가 적혀 있고, 그 근거(테스트·훅)가 저장소에서 실제로 확인되는가
  • 계획 의무 작업이 경로·유형으로 판정 가능하게 적혀 있는가
  • 계획 의무 작업의 PR에 계획 요약을 요구하는 확인 절차가 PR 템플릿(07)이나 리뷰 규칙에 반영되어 있는가
  • 우회 모드의 로컬 차단이 관리 설정으로 배포되어 있는가
  • 이 문서의 수정 경로가 CODEOWNERS에 등록되어 있는가
  • 허용 목록(allow)이 늘어나기만 하고 줄지 않는 신호(자가 진단 B-9)를 분기마다 확인하는가

PR 템플릿 예시와 작성 지침

에이전트가 만든 변경에서 가장 위험한 것은 코드에 드러나지 않는 가정이다. 본문 9장의 minishop 사고에서 개발자 A의 세션은 "할인은 주문의 것", 개발자 B의 세션은 "금액은 품목의 것"이라고 가정했다. 두 구현은 각자 테스트를 통과했으나, 결합한 뒤 장부가 맞지 않았다. 가정은 코드에 기록되지 않은 조건을 진술한 것이므로 코드를 분석해도 드러나지 않는다. 그래서 minishop 팀은 PR 템플릿에 가정 섹션을 강제로 배치했다(9.3.3). 이 문서는 그 템플릿(예제 9.11)의 원문과 각 항목이 결합 전 검증에서 맡는 역할을 설명한다.

## 결합 전 확인

- [ ] 관련 계약·명세(specs/)를 확인했고 위반이 없다
- [ ] 다른 팀원이 의존하는 인터페이스를 바꾸지 않았다 (바꿨다면 명세 변경을 포함했다)
- [ ] 계약 테스트를 포함한 전체 테스트가 통과한다
- [ ] 이 변경으로 영향받는 코드의 오너에게 리뷰를 요청했다

항목별 해설

변경 내용(세 줄 이내) — 분량 제한 자체가 점검 역할을 한다. 한 PR의 변경을 세 줄로 설명할 수 없다면 그 PR은 여러 관심사를 담고 있다. 이는 표 10.1의 분할 기준(한 문장 설명 가능성)과 같은 판정이다. "왜"를 적게 한 이유는 에이전트가 작성한 커밋 메시지가 무엇을 바꿨는지는 정확히 기록하지만 왜 바꿨는지는 담지 못하기 때문이다(10.3.1).

가정 섹션 — 이 템플릿의 존재 이유다. 세 가지 설계가 들어 있다. 첫째, 제목이 "전제하는 것"이므로 작성자가 코드 밖의 조건을 떠올린다. 둘째, "없음"도 답이다 라는 문구로 빈칸을 허용하지 않는다. 빈칸으로는 "가정이 없다"와 "생각하지 않았다"를 구분하지 못한다. "없음"이라고 적은 작성자는 최소한 한 번 자문한 것이다. 셋째, 예시 두 개가 가정의 형태를 보여 준다. 할인 배분 단위는 데이터 모델에 관한 가정이고, 재시도 안전성은 외부 동작에 관한 가정이다. 이 섹션은 기계가 대신 작성하지 못한다. 결합 전 검증 체크리스트에서 자동화 열이 "불가능"인 유일한 항목이 가정 명시다. 그래서 템플릿으로 강제한다.

결합 전 확인 네 항목 — 네 항목의 순서에는 이유가 있다. 첫째 항목인 계약 확인은 명세 부재를 방어한다. 둘째 항목인 인터페이스 변경 여부는 컨텍스트 불일치를 방어한다. 셋째 항목인 계약 테스트 포함 전체 테스트는 자동 검증에 해당한다. 넷째 항목인 오너 리뷰 요청은 CODEOWNERS로 지정된 사람이 계약의 변경을 승인하게 한다. 둘째 항목의 괄호 "(바꿨다면 명세 변경을 포함했다)"는 인터페이스 변경을 금지하는 것이 아니라 명세와 함께 변경한다는 규칙이다. 이 규칙은 병합 게이트(예제 9.12)가 pricing.py 변경 시 specs/pricing-contract.md 변경을 요구하는 검사와 짝을 이룬다.

게이트와의 관계

템플릿의 확인 항목 가운데 자동화가 가능한 항목은 CI 게이트로 옮겨 사람의 성실성에 의존하지 않게 한다(9.3.3). minishop에서는 계약 테스트 실행과 명세 변경 동반 확인이 게이트로 자동화되어 있고, 템플릿에는 그 결과를 확인했다는 체크만 남는다. 자동화된 항목을 템플릿에서 지우지 않는 이유는 작성자가 결과를 한 번 확인하게 하려는 것이다.

자기 팀에 맞출 때

항목 그대로 두는 것 바꾸는 것
변경 내용 분량 제한과 "왜" 요구 줄 수(세 줄이 표준)
가정 섹션 제목, "없음"도 답이라는 문구, 예시 2개 형식 예시를 자기 도메인의 가정으로(예: "이 잡은 하루 한 번만 실행된다")
결합 전 확인 네 항목의 순서 명세 디렉터리 경로, 계약 테스트 이름
추가 — 계획 의무 작업(06)에 해당하면 "계획 요약" 항목을 추가한다

항목을 늘릴 때는 신중해야 한다. 체크리스트가 길어지면 형식적으로 전부 체크하는 습관이 생겨 가정 섹션까지 빈칸이 된다. 본문의 계산으로는 체크리스트 10분 × PR 100건이 이틀 남짓이고, 이틀짜리 사고 하나를 방지하면 상쇄된다. 항목을 추가하려면 그 항목이 방지하는 사고가 무엇인지 설명할 수 있어야 한다.

운영 신호

  • 가정 섹션에 "없음"만 반복되면 작성자가 가정을 점검하지 않은 것이다. 리뷰에서 "정말 없는가"를 한 번 되묻고, 반복되면 8.4의 공유회에서 가정을 찾는 연습을 다룬다.
  • 게이트 위반 수(9.3.3)와 함께 "가정 섹션이 비어 있던 PR에서 발생한 결함"을 집계하면 이 템플릿의 효과가 측정된다(17.1의 품질·표준 지표).

점검

  • 저장소의 .github/pull_request_template.md에 배치되어 PR 생성 시 자동으로 채워지는가
  • 가정 섹션의 예시가 자기 팀의 도메인 가정으로 바뀌어 있는가
  • 확인 항목의 경로·테스트 이름이 실제 저장소와 일치하는가
  • 자동화 가능한 항목이 CI 게이트로 옮겨져 있는가
  • 오너 리뷰 요청이 CODEOWNERS와 연결되어 실제로 리뷰어가 자동 지정되는가

온보딩 문서 예시와 작성 지침

온보딩 문서의 독자가 둘이 되었다는 사실이 설계의 출발점이다. 신규 입사자는 혼자 합류하지 않고 에이전트 세션과 함께 합류한다(본문 8.3.1). 사람에게 필요한 것은 맥락(이 팀이 무엇을 만들고, 왜 이 구조를 택했으며, 무엇을 누구에게 물어야 하는가)이고, 에이전트에게 필요한 것은 규칙(실행 명령, 작업 규약, 금지의 경계)이다. 한 문서로 두 독자를 모두 충족하려 하면 어느 쪽에도 맞지 않는 문서가 된다.

에이전트 층은 이미 완성되어 있다. 7장에서 만든 팀 CLAUDE.md(05), 권한 정책(06), 훅과 설정이 그대로 세션의 온보딩 자료다. 입사 첫날의 세션과 3년 차의 세션이 같은 표준을 적용받는다. 따라서 새로 설계할 대상은 사람을 위한 안내 층 하나이고, 그 문서는 분량이 짧아야 한다.

# notihub 온보딩 안내

첫 주의 목표는 도구 사용법의 숙달이 아니라 팀의 작업 방식에
접속하는 것이다. 규칙의 원본은 이 문서가 아니라 아래 파일들이다.
이 문서는 읽는 순서와 물을 사람을 안내한다.

## 먼저 읽을 것 (순서대로)
1. CLAUDE.md — 저장소 구조, 명령, 작업 규약의 원본
2. docs/policies/permissions.md — 권한 정책과 그 근거
3. specs/delivery-contract.md — 발송 규칙의 계약

## 환경 준비
- 조직 계정으로 로그인한다 (개인 계정 금지)
- 저장소를 열고 워크스페이스를 신뢰하면 팀 플러그인
(notihub-kit@notihub-plugins) 설치가 제안된다. 수락한다

## 누구에게 묻는가
- 표준·규칙: @notihub/standards
- 발송 도메인: services/api/CLAUDE.md 첫머리의 담당자
- 답이 파일에 없었다면, 답을 들은 뒤 그 내용을 파일에
반영하는 PR을 올린다. 이것이 이 팀의 질문 규약이다

## 첫 주 과제
- 3일 차: onboarding 라벨의 이슈에서 하나를 골라 첫 PR을 올린다
- 5일 차: 이 문서를 포함해 온보딩 과정에서 낡았거나 틀린
  내용을 고치는 PR을 올린다

절별 해설

머리말 — 첫 문장이 온보딩의 목표를 규정한다. 목표는 도구 사용법의 숙달이 아니라 팀의 작업 방식에 접속하는 것이다. 둘째 문장은 이 문서의 성격을 규정한다. 이 문서는 규칙의 원본이 아니라 위치 안내다. 이 선언이 있어야 뒤의 절들이 짧아진다.

먼저 읽을 것(순서대로) — 규칙의 내용을 옮겨 적지 않고 원본 파일을 순서대로 가리킨다. 실행 명령과 커밋 형식은 CLAUDE.md에, 권한 정책은 정책 문서에, 도메인 규칙은 계약 문서에 있다. 복사본을 담지 않으므로 원본이 바뀌어도 이 문서를 수정할 필요가 없다(7.5.1의 참조 원칙). 온보딩 문서가 두 분기 전 구조를 설명하게 되는 문제는 대부분 복사본 때문에 생긴다.

환경 준비 — 조직 계정(개인 계정 금지)은 6.4.1의 데이터 정책과 직결된다. 개인 구독으로 업무 저장소를 열면 데이터 처리 조건이 달라진다. 팀 플러그인은 워크스페이스 신뢰 시 자동 제안(8.2.2)으로 갖춰지므로, 설치 절차를 적는 대신 "수락한다"만 남긴다.

누구에게 묻는가 — 표준 담당과 도메인 담당을 분리한다. 마지막 줄이 이 문서에서 가장 중요한 규칙이다. 답이 파일에 없었다면, 답을 들은 뒤 그 내용을 파일에 반영하는 PR을 올린다. 질문이 자산의 갱신으로 이어지는 순환이 여기서 시작된다. 이 규약이 없으면 같은 질문이 입사자마다 반복된다. 규약이 있으면 신규 입사자가 문서의 빈틈을 점검하는 역할을 한다.

첫 주 과제 — 산출물로 확인한다(8.3.2의 원칙: 이해 여부를 묻지 않고 무엇을 만들었는지 확인한다). 3일 차의 첫 PR은 onboarding 라벨 이슈, 즉 실제 백로그의 작은 항목으로 수행하고 가상 과제를 만들지 않는다. 5일 차의 문서 개선 PR은 온보딩 과정에서 발견한 낡은 내용을 고치는 과제다. 이 과제가 온보딩 문서를 갱신하는 장치 역할을 한다.

첫 주 커리큘럼 (표 8.5)

온보딩 문서는 위치만 안내하고, 일정은 운영자가 별도로 관리한다. 다음은 notihub의 닷새 일정이다.

일차 실습 산출물 확인하는 것
1일 조직 계정 인증, 팀 플러그인 설치, 저장소 탐색 세션 탐색 세션 기록 환경이 팀 표준대로 갖춰졌는가
2일 CLAUDE.md·정책 문서 정독, 가드레일 차단 체험, 권한 모드 실습 표준 요약과 질문 목록 규칙과 그 근거를 연결해 이해했는가
3일 작은 이슈로 첫 수정, /notihub-kit:commit·/notihub-kit:review 사용, PR 제출 첫 PR 팀의 작업 절차를 따라 완주했는가
4일 계약 문서 기반 작업, 리뷰 대응, 병합 병합된 PR 계약과 리뷰 체계 안에서 작업했는가
5일 첫 주 회고, 온보딩 문서 개선 PR, 개인 CLAUDE.md 시작 문서 개선 PR 온보딩에서 나온 질문이 자산의 갱신으로 이어졌는가

대상에 따라 조정한다. 에이전틱 코딩 경험자는 1·2일 차를 하루로 압축하고 4일 차 과제를 확대한다. 첫 직장인 신입은 3일 차 앞에 짝 작업 반나절을 넣는다. 세 명 규모 팀이라면 1·2일 차와 3·4일 차를 각각 하루로 합쳐 첫 PR이 병합된 PR에 흡수된 네 가지 산출물만 유지하고 사흘로 줄여도 된다. 중요한 것은 일수가 아니라 산출물로 확인하는 것이다. 2일 차의 권한 모드 실습은 같은 편집 요청을 default와 acceptEdits에서 한 번씩 실행해 승인 프롬프트의 차이를 확인하는 방식으로 구성한다. 여기에 plan에서 계획 단계에 멈추는 동작을 관찰하는 절차를 더하면 표 7.7이 암기 대상이 아니라 적용 기준으로 읽힌다.

담을 것과 담지 않을 것 (8.3.1)

구분 내용
담는 것 읽는 순서, 계정과 권한의 신청 경로, 도메인별 담당자, 첫 과제의 위치, 질문 규약
담지 않는 것 실행 명령과 커밋 형식(CLAUDE.md를 가리킨다), 권한 정책의 내용(정책 문서를 가리킨다)
경계 사례 팀의 결정 이력과 배경 설명이 길어지면 별도 문서로 분리하고 경로만 남긴다

자기 팀에 맞출 때

  • 읽을 순서의 세 파일을 자기 저장소의 실제 경로로 바꾼다. 계약 문서가 없으면 그 줄을 지우지 말고 "(작성 중 — 9.2 참고)"로 남겨 빈자리를 드러낸다.
  • 담당자는 개인 이름보다 팀 계정·그룹(@org/standards)으로 적어 담당자가 바뀌어도 유효하도록 한다.
  • 첫 주 과제의 라벨 이름과 일차는 표 8.5를 기준으로 팀 규모에 맞게 줄인다.
  • 문서가 한 화면을 넘기 시작하면 무엇이 복사본인지 찾아 원본 참조로 바꾼다.

점검

  • 규칙의 내용(명령·커밋 형식·권한 조건)이 이 문서에 복사되어 있지 않은가
  • 읽을 순서의 파일이 모두 실재하는가
  • 질문 규약(답을 들으면 파일에 반영하는 PR)이 명시되어 있는가
  • 첫 주 과제가 실제 백로그(onboarding 라벨)와 연결되어 있는가
  • 마지막 개선 PR이 언제였는가(두 분기 넘게 없다면 5일 차 과제가 작동하지 않는 것이다)

팀 스터디 가이드

『팀을 위한 클로드 코드 완벽 가이드』를 팀 단위로 학습하는 커리큘럼이다. 6주 기본 과정과 심화 2회로 구성한다. 주 1회 90분 모임을 기준으로 한다. 이 책은 개인의 사용법이 아니라 팀의 표준과 공정을 다루므로, 스터디의 목표도 "책을 다 읽는 것"이 아니라 매주 팀에 남는 산출물을 하나씩 만드는 것으로 설정한다. 6주가 끝나면 팀의 CLAUDE.md 초안, 파일럿 기준 문서, 인터페이스 계약 1건, PR 템플릿, 1차 리뷰 도입 계획이 저장소에 남아 있어야 한다.

운영 방식

모임 구성(90분)

시간 활동 진행 요령
15분 읽기 요약 진행자가 아니라 참가자 한 명이 돌아가며 그 주의 핵심을 5분 안에 정리한다
25분 실습 결과 공유 사전 실습에서 진행이 어려웠던 지점과 예상과 다른 결과를 먼저 다룬다. 성공 사례보다 실패 사례의 학습 효과가 크다
35분 토론 아래 주차별 질문을 "우리 팀에 적용하면"으로 바꿔 묻는다. 책 내용 확인이 아니라 결정을 내리는 시간이다
15분 산출물 결정 토론 결과를 산출물 초안에 반영하고 담당자와 마감을 정한다

원칙

  • 읽기와 실습은 모임 전에 각자 마친다. 모임에서 책을 읽지 않는다.
  • 산출물은 저장소의 docs/adoption/ 같은 한곳에 커밋해 스터디 자체를 기록으로 남긴다. 스터디가 끝난 뒤 이 폴더가 팀의 도입 문서가 된다.
  • 토론 질문에 정답을 맞히려 하지 않는다. 본문의 minishop·notihub 사례는 판단의 기준을 제시한 것이다. 답은 팀마다 다르다.

참가자 구성

  • 5명 이하: 전원이 전 과정을 함께 한다.
  • 6~15명: 실습 공유는 2~3명씩 소그룹으로 나누고, 토론과 산출물 결정은 전체가 한다.
  • 팀 리드·엔지니어링 매니저: 1장을 읽은 뒤 4주차(6·7장)부터 합류해도 된다. 단, 5·6주차의 계약·리뷰 결정에는 반드시 참여한다.

사전 준비(스터디 전 주)

  • 예제 저장소를 클론하고 부록 A의 실습 환경(클로드 코드, Node.js 22 이상, Python 3.11 이상, jq, gh)을 갖춘다. 각 장 폴더의 README.md를 먼저 읽는다.
  • 전원이 2장의 첫 세션 실습(hello-todo)을 마치고 모이면 1주차 토론이 구체적으로 진행된다.

여섯 항목 가운데 넷 이상이 남았다면 스터디는 목적을 달성한 것이다. 남지 않은 항목은 해당 주차의 토론이 결정으로 이어지지 않은 것이므로, 그 장만 다시 읽고 결정만 내리는 짧은 모임을 한 번 더 연다.

도입 조직 자가 진단

『팀을 위한 클로드 코드 완벽 가이드』의 본문 기준을 세 가지 진단으로 옮긴 것이다. 각 진단은 쓰는 시점과 답하는 사람이 다르다.

진단 언제 누가 무엇을 알게 되는가
A. 기반 관행 점검 도입 결정 전, 또는 도입이 기대만큼 효과가 없을 때 리드 지금 필요한 것이 도구인지 표준인지
B. 안티패턴 조기 신호 운영 중 분기마다 리드와 구성원이 각자 사고로 이어지기 전의 실패 패턴과 그 교정의 첫걸음
C. 리더 결정 점검 도입 단계가 바뀔 때마다 리드 아직 내리지 않은 결정과 그 결정을 미룬 대가

진행 방법: 구성원이 있는 진단(B)은 각자 답한 뒤 합산한다. 리드의 답과 구성원의 답이 다른 문항이 조직의 실제 상태에 가장 가깝다. 결과는 아래 기록 양식에 남겨 다음 분기와 비교한다.

진단 A — 기반 관행 점검 (본문 17.3)

안티패턴의 대부분은 기반의 부재에서 발생한다. 도구를 바꾸기 전에 다섯 가지를 확인한다.

판정: "아니오"가 세 개 이상이면 지금 필요한 것은 더 나은 도구가 아니라 표준과 도입 체계다. 이 책의 3부(6~8장)로 돌아간다. 하나 또는 둘이라면 해당 항목의 장만 먼저 읽고 4부로 진행한다.

예를 들어 1·3번만 "아니오"인 팀(PR 없이 직접 푸시, 방침 문서 없음)은 도구 도입보다 PR 기반 작업 흐름(10.1)과 팀 CLAUDE.md(05)를 먼저 만들어야 한다. 그 둘이 없으면 에이전트의 산출물을 검토할 지점도, 세션이 따를 규칙도 없다.

진단 B — 안티패턴 조기 신호 (본문 17.3, 표 17.6·17.7)

각 문항에 "예"라고 답하면 해당 안티패턴의 조기 신호가 나타난 것이다. 신호의 위치 열은 그 신호를 확인하는 곳을 가리킨다. 교정의 첫걸음 열은 지금 해야 할 일을 가리킨다.

판정과 읽는 법

  • "예"가 하나라도 있으면 해당 행의 첫걸음을 이번 분기 안에 실행한다.
  • 안티패턴은 연쇄된다(17.3.2). 리뷰 스킵(2)이 나타나면 상류의 산출량 평가(6)와 비용 방임(3)을 함께 점검한다. 활용이 위축되었다면 최근의 비용 정책을 확인한다. 신호 하나가 나타났을 때 그 상류 조건까지 점검하는 조직이 사고를 미리 막는다.
  • 교정 완료는 조치 실행이 아니라 신호의 정상화로 판정한다. 본문의 notihub는 권한 프로파일을 재적용해 allow 목록 증가를 멈췄다. 그러나 예외 신청은 늘지 않았고, 확인 결과 구성원이 개인 설정으로 우회하고 있었다. 신청서를 절반으로 줄인 뒤에야 신호가 정상으로 돌아왔다(17.3.2).

문항별 확인 방법(데이터의 출처)

# 확인 방법 비교 기준
1 차단 훅의 실행 기록(훅이 남긴 로그 또는 7.5.3의 기록 방식)을 규칙별로 집계 분기 전과 비교. 0에 수렴하거나 한 규칙이 대부분이면 신호
2 PR 생성→승인 시각의 차이를 저장소 API로 집계해 변경 줄 수와 함께 확인 줄 수 대비 검토 시간이 실제 읽기 속도보다 짧으면 신호
3 13.3.2의 주간 리포트 존재 여부 자체가 답이다 리포트가 없으면 "예"
4 무인 배치의 아침 리포트에서 실패율 추세와 대상 건수 추세를 나란히 확인 실패율↑·대상↑가 동시면 신호
5 파일럿 기준 문서(02)의 판정 기록이 있는가 기록이 없으면 "예"
6 저장소 API로 주별 PR 수와 평균 변경 줄 수를 집계 둘이 함께 증가하면 신호
7 13.2.1 분석 대시보드의 개인별 수용률·활용도 분산 분산이 분기마다 커지면 신호
8 재작업 PR 비율과 병합 충돌 건수를 동시 진행 작업 수와 함께 확인 병렬 작업 수와 함께 오르면 신호
9 settings.json의 permissions.allow 항목 수를 Git 이력으로 추적 늘기만 하고 줄어든 적이 없으면 "예"
10 리뷰 코멘트에서 주니어의 이의 제기·직접 수정 건수를 분기별로 집계 감소 추세면 신호

데이터가 없는 문항은 "확인 불가"로 기록한다. 확인 불가가 셋 이상이면 측정 체계 자체가 없다는 뜻이므로 17.1로 돌아간다.

진단 C — 리더 결정 점검 (부록 B.4, 표 B.7~B.10)

각 항목이 팀에서 "결정되어 문서로 존재하는가"를 확인한다. 오른쪽 열은 그 결정을 미루었을 때 발생하는 결과다. 미결정 항목이 곧 리드의 할 일 목록이 된다.

도입 단계 (6장)

표준과 공정 (7~10장)

품질과 거버넌스 (11~14장)

자동화와 조직 (15~17장)

판정: 부문별로 미결정 항목을 센다. 네 부문의 순서(도입 → 표준과 공정 → 품질과 거버넌스 → 자동화와 조직)는 본문의 진행 순서이자 의존 순서다. 앞 부문이 비어 있으면 뒤 부문의 결정은 실효가 없으므로, 가장 앞에서 비어 있는 부문의 장부터 읽는다. 모든 항목을 한 번에 결정할 필요는 없다. 팀이 그 단계에 도달했을 때 해당 부문이 채워져 있으면 충분하다.

결과 해석 예

가상의 12인 팀이 도입 두 분기째에 진단한 결과다.

  • 진단 A: "아니오" 1개(5번 사고 복기 절차 없음) → 기반은 갖춰졌다. 14.3.4의 플레이북만 보강한다.
  • 진단 B: 리드는 2번(리뷰 스킵)만 "예"라고 답했으나 구성원 다수는 2번과 9번(권한 방임)에 "예"라고 답했다 → 리드가 확인하지 못한 신호가 9번이다. allow 목록의 Git 이력을 확인하니 두 분기 동안 열한 항목이 늘고 하나도 줄지 않았다. 2번의 상류 조건으로 6번(산출량 평가)을 함께 점검했더니 PR 수와 평균 크기가 함께 늘고 있었다.
  • 진단 C: 도입 0 / 표준·공정 1(표준 개정 절차 미결정) / 품질·거버넌스 3(리뷰 역량 유지 장치, 권한 예외 승인 절차, 사고 대응 역할) / 자동화·조직 6 → 자동화·조직은 아직 해당 단계에 이르지 않았으므로 정상이다. 품질·거버넌스의 3건이 이번 분기의 할 일이다. 이 3건은 진단 B의 2번·9번과 정확히 겹친다.

이번 분기 조치는 세 가지로 정해졌다. 표준 개정 절차 문서화(7.5.2), 권한 예외 승인 절차와 예외 기한 설정(14.1.1, B-9의 첫걸음), 리뷰 용량 재배정과 1차 리뷰 자동화 검토(11.2, B-2의 첫걸음). 평가 기준에서 산출량을 제외하는 논의(17.4.2)는 다음 분기 안건으로 넘겼다.
