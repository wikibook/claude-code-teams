# 보안 검토 답변 양식

보안 검토에서 가장 먼저 나오는 질문은 "우리 코드가 모델 학습에 사용되는가"다. 이
질문에 예·아니오로 답하려 하면 논의가 정리되지 않는다. 답은 **어떤 계약과 사용
환경으로 서비스를 쓰는지**에 따라 달라지기 때문이다(본문 6.4.1). 이 양식은 막연한 질문
("AI에 코드를 넣어도 되는가")을 검토 가능한 질문("어떤 데이터를 어떤 조건에서 쓸 수
있는가")으로 바꾸는 회신 문서다. 보안팀·법무팀이 그대로 검토할 수 있도록 근거
문서와 확인일을 항목마다 붙인다.

## 언제, 누가 쓰는가

- 시점: 파일럿 시작 전. 보안 검토가 도입 막바지에 일정을 멈추는 일(표 B.7 "도입
  막바지에 보안 검토로 일정이 중단된다")을 막기 위해 기술 담당이 먼저 작성해 제출한다.
- 작성: 기술 담당(리드 또는 파일럿 운영자). 검토: 보안팀·법무팀.
- 파일럿 기준 문서(02)의 제외 범위와 대응한다. 02에서 배포·운영 DB를 제외했다면
  이 문서 "승인 요청 범위"의 금지 항목과 일치해야 한다.

## 양식

```markdown
# 클로드 코드 보안 검토 답변 (작성일: YYYY-MM-DD)

## 1. 계약과 적용 정책
- 계약 유형: Team / Enterprise / 클라우드 경로(Bedrock·Vertex·Foundry) 중 해당 항목
- 학습 사용: (상용 계약 기준 미사용 — 근거 문서, 확인일)
- 보존: (적용되는 보존 정책, 사용자 지정·ZDR 가능 여부 — 근거 문서, 확인일)

## 2. 데이터 범위
- 사용 저장소: (목록)
- 차단 대상: (.env, 자격 증명 파일, 생성 코드 디렉터리 등)
- 외부 전송: (연결한 MCP 서버와 각각의 용도)

## 3. 기술 통제
- 권한: (기본 권한 모드, 승인을 요구하는 작업)
- 차단: (훅과 권한 설정으로 막은 동작 목록)
- 배포: (관리 정책 파일의 적용 여부)

## 4. 계약 통제
- DPA 체결 여부, 보존 조건, 감사 지원, 데이터 처리 위치

## 5. 승인 요청 범위
- 허용: (예: 소스 저장소에서의 개발 작업)
- 조건부 허용: (예: 고객 데이터가 포함된 저장소 — 별도 승인 후)
- 금지: (예: 운영 데이터베이스 접근, 배포 조작)
```

## 항목별 작성 지침

**1. 계약과 적용 정책.** 소비자용 Free·Pro·Max는 옵트아웃 방식이므로 설정을 끄지
않으면 세션이 모델 개선에 사용될 수 있다. Team·Enterprise·API 같은 상용 서비스는
고객 콘텐츠를 학습에 쓰지 않는 것이 기본이다(6.4.1). 따라서 첫 항목은 "우리는 어떤
계약으로 쓰는가"다. 개인 구독으로 업무에 쓰는 구성원이 있다면 그 자체가 별개의
위험이므로 6.3.1의 사용 현황 목록과 대조한다. 보존은 학습과 별개의 질문이다.
학습에 쓰이지 않아도 즉시 삭제되는 것은 아니므로, 적용 보존 정책과 조정 가능 여부
(Enterprise의 사용자 지정 보존 기간, 적격 계정의 ZDR)를 따로 적는다. 근거 문서와
확인일을 붙이는 이유는 정책이 바뀌기 때문이다. 확인일이 없는 답변은 검토가 끝난
뒤의 유효 기간을 확인할 수 없다.

**2. 데이터 범위.** 검토 대상은 소스 코드만이 아니다. 대화, 프로젝트 데이터, 연결된
외부 데이터(MCP), 사용량·관리 정보까지 서비스 과정에서 처리되는 정보의 종류를
적는다. 차단 대상에는 이미 훅과 권한 규칙으로 막고 있는 경로(paylog의 .env 보호
훅 같은 실제 설정)를 예시로 제시하면 설득력이 높아진다.

**3. 기술 통제.** "유출되지 않는다"고 단정하는 대신 에이전트가 어디까지 접근하고
무엇을 실행할 수 있는지를 통제 수단으로 설명한다(6.4.2). 정리 기준은 네 가지 축이다.
접근 범위(permissions.deny와 훅으로 민감 경로 차단), 실행 범위(권한 모드와
샌드박스, 파일럿 범위에서 배포·운영 DB 제외), 통신 범위(네트워크 정책, 필요하면
클라우드 경로로 기존 클라우드의 경계 안에 배치), 정책의 강제(구성원이 임의로 해제할
수 없는 관리 정책 계층)를 각각 적는다. 파일럿 전에 경계를 정해 두었다면 "앞으로
통제하겠다"가 아니라 "현재 이 범위에서 이렇게 통제하고 있다"고 서술한다.

**4. 계약 통제.** 데이터 처리 부속서(DPA)는 개인정보와 고객 데이터의 처리 관계를
계약상으로 명확히 하는 기본 문서다. 이 항목에서 보존 조건, 감사 지원, 데이터 처리
위치를 확인한다. 규제 요건이 있는 조직은 컴플라이언스 인증과 처리 위치를 확인하고,
필요하면 클라우드 경로(6.2.1)로 기존 클라우드의 보안·네트워크 정책을 그대로
적용한다. 기술 담당은 법무팀과 보안팀이 바로 검토하도록 확인 항목을 먼저 정리하는
역할을 한다.

**5. 승인 요청 범위.** 이 문서의 결론은 승인 여부가 아니라 **사용 경계의 명문화**다.
어떤 계정으로, 어떤 저장소에서, 어떤 데이터까지, 어떤 권한과 네트워크 통제 아래
쓸 수 있는지를 허용·조건부 허용·금지로 나눠 적는다. 경계가 문서로 있으면 이후 논의는
"AI 도구를 써도 되는가"에서 "현재 경계를 어떻게 조정할 것인가"로 바뀐다.

## 작성 예 (본문 paylog 팀의 항목 구성)

```markdown
## 1. 계약과 적용 정책
- 계약 유형: Team
- 학습 사용: 상용 계약 기준 미사용 (상용 이용약관 §X, 2026-08-20 확인)
- 보존: 서비스 표준 보존 정책 (개인정보 처리방침, 2026-08-20 확인)

## 2. 데이터 범위
- 사용 저장소: paylog
- 차단 대상: .env 계열, 자격 증명 파일, dist/ 생성 코드
- 외부 전송: Jira MCP(이슈 조회·생성)

## 3. 기술 통제
- 권한: 기본 default, 파일 편집·명령 실행에 승인 요구
- 차단: .env 읽기·쓰기(훅 protect_env.py), 운영 DB 접속 명령(permissions.deny)
- 배포: 관리 정책 파일 미적용(파일럿 단계, 확산 시 적용 예정)

## 5. 승인 요청 범위
- 허용: paylog 저장소에서의 개발 작업
- 조건부 허용: 고객 데이터가 포함된 저장소(별도 승인 후)
- 금지: 운영 데이터베이스 접근, 배포 조작
```

근거 문서의 조항 번호와 확인일은 실제 값으로 채운다. 위 예의 조항 표기는 자리
표시자다.

## 제출 전 점검

- [ ] 1번의 학습·보존 항목에 근거 문서와 확인일이 모두 붙어 있는가
- [ ] 2번의 차단 대상이 3번의 차단 수단(훅·권한 규칙)과 대응하는가(선언만 있고 수단이 없는 항목은 없는가)
- [ ] 5번의 금지 항목이 파일럿 기준 문서(02)의 제외 범위와 일치하는가
- [ ] 개인 구독으로 업무에 쓰는 구성원이 있다면 그 사실과 통일 계획을 적었는가
- [ ] 도입 후 경계가 지켜지는지 확인할 운영 수단(14장의 로그, 공급망 관리, 사고 대응)을 후속 과제로 명시했는가
