# 파일럿 기준 문서 양식

파일럿의 성패는 도구가 아니라 **시작 전에 무엇을 확정했는가**에 따라 결정된다.
성공 기준이 없으면 결과에 따라 기준이 바뀐다. 실패 기준이 없으면 성과가 불분명한
상황에서 "조금 더 써 보자"는 결정이 반복되고, 파일럿이 끝나지 않은 채 사실상 정식
도입으로 이어진다(본문 6.1.2). 이 문서는 팀·기간·범위·성공 기준·실패 기준·측정 방법을 파일럿 시작
전에 한 장으로 고정하고, 종료 시점에 같은 문서로 판정하기 위한 양식이다.

## 작성 전에 정할 것: 파일럿 팀 선정 (6.1.1)

기준 문서를 쓰기 전에 팀이 관찰에 적합한지 먼저 확인한다. 부적합 조건에서 시작하면
도구의 효과와 환경의 문제를 구분할 수 없다.

| 기준 | 적합 | 부적합 | 이유 |
|---|---|---|---|
| 규모 | 개발자 3~8인 | 1~2인, 15인 이상 | 너무 적으면 개인 습관과 도구 효과가 섞이고, 너무 많으면 관찰의 질이 떨어진다 |
| 코드베이스 | 테스트가 있고 배포가 자동화된 저장소 | 검증 수단이 없는 저장소 | 산출물의 품질을 기존 공정 안에서 확인할 수 있어야 한다 |
| 의지 | 자원자가 있고 리더가 참여 시간을 승인한 팀 | 지명으로 차출된 팀 | 자원한 팀이 실패 사례까지 공유한다. 회의적인 구성원 한둘은 오히려 유익하다 |
| 일정 | 통상 업무 기간 | 대형 릴리스 직전, 비상 대응 중 | 여유가 없으면 도구를 사용하지 않은 것과 사용할 수 없었던 것을 구분할 수 없다 |

기간은 4~8주가 적절하다. 첫 주는 설치·인증·기본 사용에 쓰이므로 4주 미만이면
학습 과정만 측정하게 된다. 기간이 너무 길면 임시 실험이 상시 운영으로 굳어진다.

## 양식

```markdown
# 파일럿 기준 (작성일: YYYY-MM-DD)

## 대상과 기간
- 팀: (팀명, 개발자 N명)
- 저장소: (저장소 이름)
- 기간: YYYY-MM-DD ~ YYYY-MM-DD (N주)
- 제외 범위: (파일럿에서 다루지 않는 작업 — 예: 운영 DB 접근, 배포 조작)

## 성공 기준 (모두 충족하면 확산 제안)
- 채택: (주간 활성 사용 비율 등)
- 산출: (착수→병합 시간, 병합 PR 수 등)
- 품질: (반려율·결함률이 악화되지 않을 것)
- 체감: ("계속 사용하겠다" 응답 비율)

## 실패 기준 (하나라도 해당하면 종료)
- 사용 정착: (N주 차 이후 활성 비율이 기준 아래로 떨어지고 회복되지 않는 경우)
- 품질 악화: (품질 지표가 유의미하게 나빠지고 원인이 도구로 좁혀지는 경우)
- 보안 차단: (보안 검토에서 해소할 수 없는 차단 사유가 확인되는 경우)

## 측정과 판정
- 측정: (주기, 담당자, 데이터 출처)
- 판정: (어느 주차의 데이터로, 누가 결정하는가)
- 지표는 판정에만 사용하고 개인 평가와 분리한다
```

## 항목별 작성 지침

**성공 기준은 세 종류를 모두 둔다(6.1.2).** 채택 지표는 다른 지표를 해석하기 위한
전제다. 채택률이 낮으면 산출물이 개선되었더라도 충분한 사용 경험을 확보한 것이
아니다. 산출 지표는 속도와 품질을 함께 본다. PR 수가 늘었는데 반려율과 결함률도
늘었다면 생산성 향상이 아니라 검증 공백의 확대다. 체감 지표는 주간 설문 한두 문항
("이번 주 에이전트가 시간을 절약하는 데 도움이 되었는가", "다음 프로젝트에서도
계속 사용하겠는가")이면 충분하다. 이 응답은 도구가 실제 업무에 정착할 가능성을
나타낸다.

**실패 기준은 성공 기준과 같은 날 정한다.** 세 가지 유형이 표준이다. 사용 정착
실패는 4주 차 이후 활성 비율이 절반 아래로 떨어지고 회복되지 않는 경우다. 품질
악화는 속도가 올랐더라도 확산을 멈추는 사유가 된다. 보안 차단은 기술적 성과와
무관하게 종료 사유다. 실패로 판정되면 계약을 정리하고 관찰 기록을 남긴 뒤 종료한다.
실패의 원인과 조건은 다음 파일럿의 설계 자료이므로, 실패도 파일럿의 중요한 결과다.

**측정 방법은 시작 전에 확정한다.** 착수→병합 시간과 반려율은 저장소와 이슈
트래커에서, 사용량은 조직의 관리 화면에서 수집한다. 파일럿에서는 이 정도의 단순한
수집 체계로 충분하다. 상시 측정 체계로의 확장은 17장의 문제다.

**지표를 개인 평가와 분리한다는 문장은 형식이 아니다.** 지표가 평가에 쓰인다는
인식이 생기면 채택률과 산출 수치가 왜곡된다. 그 결과 파일럿은 도구를 관찰하는
실험에서 성과를 보여 주는 수단으로 변질된다.

## 작성 예 (본문 paylog 팀)

```markdown
# 파일럿 기준 (작성일: 2026-08-20)

## 대상과 기간
- 팀: 결제 서비스팀(개발자 5명)
- 저장소: paylog
- 기간: 2026-09-01 ~ 2026-10-12 (6주)
- 제외 범위: 운영 데이터베이스 접근, 배포 조작

## 성공 기준 (모두 충족하면 확산 제안)
- 채택: 주간 활성 사용 80% 이상 유지
- 산출: 착수부터 병합까지 걸리는 시간 20% 단축
- 품질: PR 반려율과 결함 발생률이 나빠지지 않을 것
- 체감: "계속 사용하겠다" 응답 70% 이상

## 실패 기준 (하나라도 해당하면 종료)
- 4주 차 이후 주간 활성 사용 50% 미만이 2주 연속
- 결함 발생률이 뚜렷하게 증가하고 원인이 도구로 좁혀짐
- 보안 검토에서 해소할 수 없는 차단 사유 확인

## 측정과 판정
- 측정: 매주 금요일, 운영 책임자가 기록
- 판정: 5~6주 차 데이터를 기준으로 결정
- 지표는 판정에만 사용하고 개인 평가와 분리한다
```

수치는 조직마다 다르게 정해도 되지만 구조는 같다. 채택을 확인하고, 속도와 품질을
함께 측정하고, 사용자 수용도를 확인한다. 제외 범위에 배포와 운영 DB를 넣은 것은
6.4.2의 실행 범위 통제와 같은 원칙이다. 이 기록은 보안 검토 답변(03)에서 "현재
이 범위에서 이렇게 통제하고 있다"고 서술하는 근거가 된다.

## 판정 시 점검

- [ ] 성공 기준 네 항목의 실측값이 모두 기록되어 있는가(하나라도 미측정이면 판정을 미루지 말고 "측정 실패"로 기록한다)
- [ ] 산출 지표에서 속도 향상이 품질 악화와 동반되지 않았는가
- [ ] 실패 기준 셋 중 어느 것도 발동하지 않았는가
- [ ] 판정 결과와 근거를 확산 일정(6.1.3)의 첫 판정 지점 기록으로 남겼는가
