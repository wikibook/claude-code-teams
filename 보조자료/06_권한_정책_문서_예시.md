# 권한 정책 문서 예시와 작성 지침

권한 규칙이 개별 도구 호출의 경계를 정한다면, 권한 모드는 세션 전체의 실행 방식을
정한다. 팀 정책은 이를 한 단계 확장해 **어떤 작업에 어떤 모드를 적용할 것인지**를
정하는 문서다(본문 7.3.2). 모드 선택의 기준은 작업의 위험도가 아니라 **검증 체계의
구조**다. 산출물이 테스트와 자동 검증으로 충분히 확인되는 작업은 승인 빈도를 낮춰도
안전하다. 반면 검증이 사람의 판단에 의존하는 작업에서는 승인 자체가 검증 지점이므로,
승인을 줄이는 것이 곧 검증 수준의 저하다. 권한 수준은 리뷰와 테스트가 제공하는 검증
강도에 맞춘다(2.7.2).

## 예시 원문 (notihub/docs/policies/permissions.md)

```markdown
# 권한 정책

## 기본 모드
- 이 저장소의 기본 모드는 acceptEdits다 (.claude/settings.json에 설정됨)
- 근거: 전 패키지에 테스트가 있고 커밋 전 검증 훅이 있다

## 계획 검토가 의무인 작업
다음 작업은 플랜 모드로 시작하고, 계획 승인 후 구현한다.
- 저장 형식(스키마·마이그레이션)이 바뀌는 작업
- 공개 API의 추가·변경·삭제
- 발송 파이프라인(services/api/src/dispatch/)의 변경
- 세 개 이상의 작업 공간을 가로지르는 리팩터링
확인: 해당 유형의 PR은 본문에 계획 요약을 포함한다.

## 우회 모드(bypassPermissions)의 사용 조건
- 허용: 자격 증명과 운영 자원에서 격리된 컨테이너·CI 환경
- 금지: 개발자 로컬 기기 (관리 설정으로 차단됨)
- 거부 규칙은 우회 모드에서도 적용된다

## 이 문서의 수정
- .claude/ 경로와 같은 승인 절차를 따른다 (CODEOWNERS 참조)
```

## 절별 해설

**기본 모드와 근거** — 모드만 적지 않고 근거를 적는 것이 이 문서의 핵심 형식이다.
notihub가 acceptEdits를 기본으로 둔 이유는 "전 패키지에 테스트가 있고 커밋 전 검증
훅이 있다"는 검증 체계에 있다. 근거가 사라지면, 즉 테스트가 없는 패키지가 생기면
모드도 다시 판단해야 한다. 근거가 적혀 있어야 분기 점검에서 그 판단을 다시 수행한다.
검증 수단이 부족한 레거시 저장소라면 승인 과정이 주요 검증 수단이므로 default를
기본 모드로 둔다(표 7.7).

**계획 검토가 의무인 작업** — 3.1.3의 원리(계획의 가치는 변경을 되돌리는 비용에
비례한다)를 개인의 감각이 아니라 **작업 유형**으로 구체화한 절이다. 네 유형은 데이터
구조 변경, 공개 인터페이스 변경, 핵심 파이프라인 변경, 범위가 넓은 리팩터링이다.
마지막 줄 "확인: 해당 유형의 PR은 본문에 계획 요약을 포함한다"가 중요하다. 플랜
모드는 세션의 상태이므로 설정만으로 강제되지 않는다. 그래서 PR에서 계획의 존재를
확인하는 방식으로 보완한다. 목적은 특정 모드의 강제가 아니라 되돌림 비용이 큰 작업에
구현 전 검토 지점을 두는 것이다.

**우회 모드의 사용 조건** — 금지가 아니라 **환경 제한**이다. bypassPermissions는
승인 프롬프트를 생략하므로 프롬프트 주입 방어가 약해진다(2.7.1). 따라서 자격 증명과
운영 자원에서 격리된 컨테이너·CI에서만 허용하고, 로컬 기기에서는 관리 설정으로
차단한다. "거부 규칙은 우회 모드에서도 적용된다"는 문장은 권한 모드와 안전 정책이
다른 계층이라는 사실(2.7.2)을 구성원에게 알리는 역할을 한다.

**이 문서의 수정** — 정책 문서 자체가 표준이므로 수정에는 .claude/ 설정과 같은 승인
절차를 적용한다(7.5.2). CODEOWNERS로 리뷰어를 지정해 두면 정책이 합의 없이 바뀌는
일을 방지한다.

## 작업 상황별 권장 모드 (표 7.7)

자기 팀의 기본 모드와 예외를 정할 때 참고한다.

| 작업 상황 | 권장 모드 | 근거 |
|---|---|---|
| 일상 개발(테스트가 갖추어진 저장소) | acceptEdits | 편집과 작업 디렉터리 안의 파일 명령은 자동 승인. 이탈은 테스트와 diff 검토로 검증 |
| 코드베이스 조사·리뷰 | plan 또는 default | 변경보다 구조와 근거의 파악이 목적이므로 편집을 제한 |
| 설계 변경·마이그레이션 | plan으로 시작 | 되돌림 비용이 큰 변경의 검토 지점을 앞당김 |
| 검증 수단이 부족한 레거시 | default | 승인 과정이 주요 검증 수단이므로 승인 수준을 유지 |
| 프로덕션 인접 작업 | default + 거부 규칙 | 권한 모드와 별개로 적용되는 거부 규칙을 추가 |
| 격리 환경의 배치 작업 | bypassPermissions | 실행 환경의 격리를 전제로 자동 실행을 허용 |

## 자기 팀에 맞출 때

1. **기본 모드는 검증 체계에서 역산한다.** 테스트 커버리지와 커밋 전 훅이 있는가를
   먼저 확인하고, 그 사실을 근거 줄에 적는다. 근거를 적을 수 없으면 기본 모드는
   default다.
2. **계획 의무 작업은 저장소의 실제 경로로 적는다.** "핵심 파이프라인"이라는 일반어
   대신 notihub처럼 `services/api/src/dispatch/` 같은 경로를 명시해야 해당 여부에
   이견이 생기지 않는다.
3. **우회 모드의 허용 환경을 조직의 실제 CI·컨테이너 이름으로 적는다.** 이어서 로컬
   차단이 관리 설정(14.3.1)으로 실제로 배포되어 있는지 확인한다. 문서만 있고 설정이
   없으면 이 절은 권고에 그친다.
4. **CLAUDE.md의 작업 규약에는 이 문서의 위치만 남긴다**(05). 판정 기준의 원본은
   여기 한 곳이다.

## 점검

- [ ] 기본 모드에 근거가 적혀 있고, 그 근거(테스트·훅)가 저장소에서 실제로 확인되는가
- [ ] 계획 의무 작업이 경로·유형으로 판정 가능하게 적혀 있는가
- [ ] 계획 의무 작업의 PR에 계획 요약을 요구하는 확인 절차가 PR 템플릿(07)이나 리뷰 규칙에 반영되어 있는가
- [ ] 우회 모드의 로컬 차단이 관리 설정으로 배포되어 있는가
- [ ] 이 문서의 수정 경로가 CODEOWNERS에 등록되어 있는가
- [ ] 허용 목록(allow)이 늘어나기만 하고 줄지 않는 신호(자가 진단 B-9)를 분기마다 확인하는가
