# 팀 공통 CLAUDE.md 예시와 작성 지침

팀 공통 CLAUDE.md는 저장소를 여는 모든 세션이 시작할 때 읽는 규칙 파일이다. 수록
항목은 두 질문으로 판단한다. **팀 전원에게 적용되는가? 세션마다 필요한가?** 두 조건을
모두 충족하는 항목만 남긴다(본문 7.1.1). 개인 파일(4.1.1)에서 적용하던 빈도와
지속성 기준에 더해, 팀 파일에서는 공통성이 결정적 기준이 된다.

이 문서는 본문 예제 7.1(notihub 팀의 실제 파일)을 원문 그대로 싣는다. 이어서 각 절이
그 자리에 있는 이유와 자기 팀에 맞출 때 변경할 항목을 해설한다.

## 예시 원문 (notihub/CLAUDE.md)

```markdown
# notihub

사내 알림 서비스 모노레포. 각 팀의 시스템에서 이벤트를 받아
슬랙·이메일·웹훅 채널로 알림을 발송한다.

## 구조
- services/api — 알림 API와 발송 파이프라인. 발송 로직의 진실 원천
- services/web — 관리 콘솔 (React)
- packages/shared — 공용 타입과 알림 템플릿 엔진

## 명령
- 명령은 각 작업 공간 디렉터리에서 실행한다 (예: services/api에서 pnpm test)
- 전체 타입 검사는 루트에서 pnpm -r check (커밋 전 훅이 자동 실행)

## 계약
- 발송 규칙(재시도·중복 제거)을 다루는 코드는 specs/delivery-contract.md를 따른다
- 발송 파이프라인의 세부 관례는 services/api/CLAUDE.md를 따른다

## 작업 규약
- 커밋 첫 줄은 "영역: 변경 요약" 형식 (예: api: 재시도 간격 상한 추가)
- 리뷰는 /review, 커밋은 /commit을 사용한다
- 계획 검토가 의무인 작업 유형은 docs/policies/permissions.md를 따른다

## 금지
- 운영 발송 채널 호출 금지 (훅으로 차단됨) — 테스트는 샌드박스 채널 사용
- .env 계열 파일은 읽지 않는다 (권한 규칙으로 차단됨)
```

전체가 스무 줄 남짓이다. 분량이 짧은 것은 의도된 구성이다. 이 파일은 모든 세션의
시작 컨텍스트에 실리므로(2.6, 4.3), 한 줄이 늘면 팀 전체의 모든 세션이 그만큼을
매번 읽는다.

## 절별 해설

**머리말(무엇을 만드는가)** — 두 문장으로 쓴다. 에이전트가 저장소의 목적을 알아야
판단의 방향이 잡힌다. 배경 설명이나 역사는 넣지 않는다.

**구조** — 디렉터리 자체가 아니라 **디렉터리의 역할**을 적는다. "발송 로직의 진실
원천"처럼 어디가 기준인지 밝히는 한 구절이 에이전트의 탐색 순서를 결정한다. 디렉터리
목록 전체를 나열하는 것은 파생 가능한 정보(에이전트가 읽어서 알 수 있는 것)이므로
넣지 않는다(4.1.2, /doctor가 지적하는 항목).

**명령** — 실행 위치와 검사 명령을 적는다. "커밋 전 훅이 자동 실행"처럼 사람이 직접
수행하지 않아도 되는 항목을 밝혀 두면 에이전트가 불필요한 명령을 반복하지 않는다.
이 절은 실제 저장소의 스크립트와 문자 단위로 일치해야 한다. 명령 한 줄이 어긋나면
세션마다 실패가 발생한다.

**계약** — 팀 파일에서 가장 중요한 절이다. 여러 사람이 동시에 에이전트를 사용하면
세션마다 다른 가정으로 코드가 작성된다. 계약 문서의 위치를 여기에 한 줄로 고정하면
어느 구성원의 세션이든 같은 계약을 참조한다(7.1.1). 지시할 때마다 계약을 언급하는
방식은 기억에 의존하므로 일관성이 깨진다. 하위 디렉터리의 CLAUDE.md로 세부 관례를
위임하는 줄도 여기 둔다. 루트에는 방향을 두고, 세부 관례는 작업 영역에 가까운 파일에
둔다(4.2.1).

**작업 규약** — 커밋 형식, 사용할 커맨드, 계획 검토 의무 작업을 적는다. 세부 판정
기준은 정책 문서(06)에 두고 여기서는 위치만 가리킨다. 규약 전체를 여기에 적으면
파일이 길어지고, 정책이 바뀔 때 두 곳을 수정해야 한다.

**금지** — 각 항목 뒤에 붙은 "(훅으로 차단됨)", "(권한 규칙으로 차단됨)" 같은 괄호가
핵심이다. CLAUDE.md는 지침을 제공하는 계층이지 실행을 보장하는 계층이 아니다(7.1.1).
컨텍스트가 압축되거나 지침이 누락되어도 반드시 지켜져야 하는 규칙은 훅·권한 규칙으로
강제하고, 여기에는 그 사실을 알린다. 문서에만 있는 금지는 권고에 그친다.

## 자기 팀에 맞출 때 바꾸는 것

| 절 | 그대로 두는 것 | 팀에 맞춰 바꾸는 것 |
|---|---|---|
| 머리말 | 두 문장 분량 | 서비스 설명 |
| 구조 | "역할"을 적는 방식 | 작업 공간과 진실 원천의 위치 |
| 명령 | 실행 위치·검사 명령·자동 실행 표시 | 패키지 관리자와 스크립트 이름 |
| 계약 | 계약 문서를 한 줄로 가리키는 구조 | 계약 문서의 경로(없다면 9.2에서 먼저 만든다) |
| 작업 규약 | 커맨드 이름, 정책 문서 위임 | 커밋 형식 |
| 금지 | 강제 수단을 괄호로 밝히는 방식 | 금지 항목과 그 강제 수단 |

## 넣지 말아야 할 것 (7.1.1)

- **개인의 취향**: "응답은 간결하게", "설명보다 코드 먼저"는 작업 방식의 선호다.
  팀 파일에 넣으면 다른 구성원의 방식과 충돌한다. `~/.claude/CLAUDE.md`에 둔다.
- **수명이 끝난 규칙**: 마이그레이션이 끝난 뒤의 "구 API 금지", 담당자가 바뀐 뒤의
  "배포 전 OOO에게 확인"은 에이전트를 잘못된 방향으로 이끌고 컨텍스트만 차지한다.
- **시스템으로 강제해야 하는 규칙**: "프로덕션 DB에 접속하지 않는다"는 문서가 아니라
  권한 정책이나 훅으로 차단해야 한다. 문서에는 강제된 사실만 알린다.

## 초안을 만드는 방법

구성원들의 기존 개인 CLAUDE.md에서 공통 항목을 추출한다. 여러 사람에게 반복해서
등장하는 규칙을 후보로 모은 뒤, 두 질문(전원 적용? 세션마다 필요?)으로 거른다. 여러
사람이 독립적으로 같은 지침을 작성했다면 그 규칙은 팀 전체에 해당하는 사실이다.
파일럿을 거친 조직은 파일럿 팀의 파일을 출발점으로 삼되 개인 취향·낡은 규칙·강제
규칙을 제거한다.

## 점검

- [ ] 각 줄이 두 질문(팀 전원에게 적용되는가, 세션마다 필요한가)을 통과하는가
- [ ] 명령 절의 명령이 실제 저장소에서 그대로 실행되는가
- [ ] 계약 문서의 경로가 실재하며, 계약 문서에 메타 정보·결정·불변식·인터페이스·이유·변경 절차가 있는가(표 9.2)
- [ ] 금지 항목마다 강제 수단(훅·권한 규칙)이 실재하는가(없다면 "금지"가 아니라 "권고"로 옮긴다)
- [ ] 개정 절차가 정해져 있는가(7.5.2). 이 파일의 수정은 CODEOWNERS로 리뷰어를 지정한다
